### 2026-07-24 — Incident Response — Kinmoon Storage Pool 1 RAID 1 Rebuild Failures, Root Cause Identified, Emergency Backup
- Continuation of Hard Drive 1 replacement from 2026-07-23; new 3TB Seagate IronWolf installed in Bay 1, detected healthy by UGOS
- Storage Pool 1 RAID 1 rebuild attempted twice (2026-07-24 01:32:29 and auto-resumed ~07:06), both failed after ~3 hours and ~5+ hours respectively; currently Degraded, rebuild stopped pending root cause resolution
- **Root cause identified via UGOS event log export and web research:** Hard Drive 2 throws deterministic "failed command: WRITE FPDMA QUEUED" (Serious level) error ~18-19 seconds after every boot/reboot; not a drive health issue (SMART data healthy, Reallocated Sector Count 99 vs. threshold 10), but a known UGREEN DXP2800 hardware/firmware incompatibility at SATA 6.0Gbps link speed with some drive models' narrow signal timing tolerance
- **Known issue confirmed via UGREEN DACH community forum (30+ pages, active thread) and independent troubleshooting (rack2reality.com May 2026):** UGREEN support directly identified the cause and published workaround
- **Fix identified (not yet applied):** force SATA link speed down to 3.0Gbps via kernel boot parameter `libata.force=3.0Gbps`, added to `/boot/EFI/debian/grub.cfg` and `/boot/EFI/debian/grub.am` in vmlinuz boot lines; requires SSH access, file backups, reboot, and verification via `/proc/cmdline`; may require rechecking after future UGOS firmware updates
- Discovered silent UGOS auto-update occurred during incident (2026-07-24 01:23:14, upgraded to v1.17.0.0095, self-triggered reboot) immediately preceding first Hard Drive 2 fault
- Reviewed UGOS event log history: WRITE FPDMA QUEUED signature intermittently present since March 2026 on both drives at different times (2026-03-02, 03-12, 05-08 x2, 05-13/14, 07-23, 07-24), and also a 2026-05-14 06:57 "Failed to detect the hard drive in slot ata1" event; suggests Hard Drive 1's original "failure" triggering this whole incident may have been accelerated or caused by this SATA link instability rather than pure media wear
- **Decided to deprioritize RAID rebuild fix pending data safety:** identified that Kinmoon's vzdump backup archive (1.3TB) is the sole copy of all Proxmox VM/container backup history, unlike Nextcloud data which primarily lives on Kuromoon hdd-backup-1/2 — treating backup data safety as higher priority than completing RAID rebuild while Kinmoon is unstable

- Disabled backup-daily vzdump job (`enabled 0` in `/etc/pve/jobs.cfg`) at ~01:30 to prevent 02:00 scheduled run from adding write load during RAID rebuild attempts; remains disabled as of session end — must be re-enabled once Kinmoon confirmed stable
- Confirmed Proxmox GUI "Enable" toggle on backup-daily job would not persist; worked around via direct `/etc/pve/jobs.cfg` CLI edit (pmxcfs hot-loads changes without service restart)
- Decision: defer applying libata.force=3.0Gbps GRUB boot parameter fix until after emergency backup completes, to avoid risk of boot config corruption while Kinmoon holds sole copy of backup data
- Decision: skip third RAID rebuild retry after second consecutive failure, once failure pattern was confirmed deterministic (same ~18-19 second post-boot fault both times) rather than random
