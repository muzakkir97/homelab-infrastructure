### 2026-09-21 - Elevated Kinmoon drive replacement to higher priority
**Decision:** Given kinmoon-smb's 95% capacity (2.6TB / 2.7TB used) combined with the previously documented failing Hard Drive 1 (July 23, 2026 SMART status degradation), and the plausible (though unproven) link to tonight's Kuromoon host freeze via CIFS I/O stalls, decided this should now be treated as an active risk to Kuromoon's own stability rather than an isolated NAS maintenance item. The kinmoon-smb storage backs critical Kuromoon backups and Proxmox infrastructure; a drive failure during I/O-heavy operations could cascade into host-level unresponsiveness as witnessed on 2026-09-21.
**Why:** The Kuromoon host-wide freeze on 2026-09-21 (pveproxy, sshd, and CT 203 all unresponsive) had no conclusively identified root cause, but the most plausible theory is an I/O stall or hang on the kinmoon-smb CIFS mount due to the NAS's failing hardware and the share's near-full capacity. Even if unproven, the risk profile is now high enough to warrant prioritization: a failing drive in active use (backing frequent rsync backup operations) is more likely to cause problems sooner rather than later. Deferring this work increases exposure.
**Alternatives considered:** Continue monitoring kinmoon-smb capacity and only replace the drive if it actually fails (rejected — reactive approach increases downtime risk; proactive replacement while still functional is safer), free up space on kinmoon-smb without replacing the drive (rejected — doesn't address the underlying hardware degradation), assume the Kuromoon freeze was unrelated to the NAS and leave both as low-priority items (rejected — the CIFS connection is a plausible vector, and simultaneous high-risk conditions warrant consolidation).

### 2026-09-21 - Stopped pursuing further root-cause forensics for Kuromoon freeze
**Decision:** After checking ZFS pool health (confirmed healthy, rpool ONLINE with no errors), disk space (1% used, 676GB free on root), journald history (mysteriously stopped logging on 2026-09-03, but shows normal activity up to that point), dmesg (buffer empty after reboot), and `/sys/fs/pstore` crash dumps (also empty), decided the incident's exact trigger cannot be conclusively proven. The monitoring stack (Prometheus/Grafana, CT 203) that would have shown pre-freeze resource metrics was itself hosted on Kuromoon and went down with it, and the reboot cleared the kernel's in-memory diagnostic buffers. Resolved the immediate issue via hard power cycle at 20:37 UTC; service restored.
**Why:** Further live diagnosis was not yielding leads, and prolonged downtime while pursuing root cause had its own cost. The forensic tools that would normally reveal the problem (crash dumps, journald entries during the incident, Prometheus metrics from the freeze window) were either unavailable or lost during the reboot. Without conclusive evidence, continued troubleshooting would be speculative. The most plausible theory (kinmoon-smb CIFS I/O stall due to 95% capacity and failing NAS hardware) was elevated to a separate decision, shifting the focus from "prove what happened" to "mitigate the likely contributing factors."
**Alternatives considered:** Keep Kuromoon in frozen state longer to attempt live diagnosis via physical console (rejected — no clear diagnostic path was working, and the monitoring stack was down, making live observation difficult), schedule an extended maintenance window to reproduce the issue (rejected — impractical and risky; service restoration took priority), assume the freeze will not recur and close the investigation (rejected — lack of root cause means no assurance against recurrence; preventive mitigation via the Kinmoon drive replacement addresses the most likely vector).

### 2026-09-21 - Added temporary VLAN20→VLAN10 firewall pass rules for direct Kuromoon management access
**Decision:** Added two explicit pass rules on pfSense's VLAN20_MAIN interface to allow direct troubleshooting access from Minimoon (192.168.20.101) to Kuromoon (192.168.10.5) during the 2026-09-21 incident: (1) **"USER_RULE: Minimoon to Proxmox GUI"** — Pass, TCP, port 8006, and (2) **"USER_RULE: Minimoon to Kuromoon SSH (temp)"** — Pass, TCP, port 22. Both rules were placed above the existing "Block all private networks" rule so they're evaluated first. This was necessary because VLAN10_MGMT had no prior explicit allow rule from VLAN20_MAIN at all — the existing ruleset only permitted VLAN20 → VLAN30 for specific web/game/DNS ports. Rather than relying solely on pfSense's physical console (which is inconvenient for routine access), these temporary rules enabled rapid web UI and SSH access to the affected host.
**Why:** Network troubleshooting is faster and more practical via direct IP access rather than through a physical serial console. The incident investigation required frequent access to Proxmox's web UI and Kuromoon's SSH shell; adding temporary rules was justified by the operational need, and they were explicitly marked as temporary pending a decision on the network's intended management-access model. The rules are scoped to a single source IP (Minimoon only), limiting their blast radius.
**Alternatives considered:** Continue to rely solely on pfSense's physical console for all management access to VLAN10 hosts (rejected — impractical for routine troubleshooting; console access is slower and requires physical presence or serial-over-IP, which is not configured), open all VLAN20 → VLAN10 traffic (rejected — too broad; the scoped rule is more secure), request a formal network redesign before adding any rules (rejected — the incident required immediate access; formal redesign can follow separately).

### 2026-08-01 - Kinmoon Storage Pool 1: destroy and recreate from emergency backup instead of further incremental rebuild troubleshooting
**Decision:** After four total failed RAID 1 rebuild/recovery attempts (two on 2026-07-24, two more on 2026-07-30/31), abandoned incremental troubleshooting in favor of a full destroy-and-recreate of Storage Pool 1 from scratch, then restore all data from the Kuromoon emergency backup copy (started 2026-07-24, verified 1.2TB match on 2026-07-31). Executed: full pool/volume deletion, fresh RAID 1 creation with new UUID `5bb187d0:b14f67a3:9f4d8ab9:16d079f8`, shared folder recreation, and complete data restore via rsync from `/mnt/hdd-backup-2/kinmoon-emergency-backup/`. Pool status confirmed **Normal/clean** with both drives `active sync` and zero spares as of 2026-07-31 01:10 UTC. The `libata.force=3.0Gbps` GRUB fix (applied to both `grub.cfg` and `grub.am` template) confirmed working — zero `WRITE FPDMA QUEUED` errors observed during the rebuild and full 1.2TB data restore. All three rebuild failures were caused by intermittent interruptions (variously attributed to the UGOS `storage_serv` monitor bug, HDD hibernation, ATA power management, or unknown causes); each mitigation (stopping `storage_serv`, disabling HDD sleep, disabling ATA power management) failed to resolve the issue on subsequent attempts. A fourth attempt with `storage_serv` stopped throughout showed the interruption was not solely caused by the software bug, suggesting a deeper or multifactorial issue. Root cause of final failure never identified, but this no longer matters — the array is healthy and data is restored.
**Why:** After four failed attempts with progressively more extensive investigation and mitigation, further incremental troubleshooting was returning diminishing insight per unit time spent. The emergency backup was already secured on 2026-07-24 and verified; destroying and recreating the array eliminated the unknown failure mode entirely, restored full redundancy faster than continued diagnosis could have, and achieved the actual goal (data safety and RAID 1 availability) without resolving the underlying cause. This is a pragmatic shift from "debug and fix the broken thing" to "replace the broken thing with a known-good one." The cost was one pool recreation (a few hours of work) versus potentially days of further troubleshooting with no guarantee of resolution. Decided to accept permanent loss of the July 12, 2026 dated LXC backup files (containers 202, 203, others) and one CT211 file, which were already unreadable due to bad sectors on the old Hard Drive 2 before the pool was wiped; newer backups exist for the same containers, making this low-impact.
**Alternatives considered:** Continue incremental rebuild troubleshooting until root cause is identified (rejected — diminishing returns after four attempts; could consume days with no resolution guarantee), attempt to recover data from the partially-wiped old array (rejected — already unreadable due to bad sectors, and the emergency backup is known good), recreate the array and leave it without data until a future recovery attempt (rejected — defeats the purpose; data restoration is the critical goal). Perform manual file-by-file recovery from the emergency backup instead of full rsync (rejected — rsync is faster and more reliable for 1.2TB of data).

### 2026-08-01 - Kinmoon: disable HDD sleep and ATA power management as precaution during RAID recovery
**Decision:** Disabled both "Enable hard drive sleep" and "Enable USB hard drive sleep" in UGOS Hardware & Power settings as a precautionary measure during RAID rebuild/recovery attempts. The UGOS UI reported "Operation failed" when trying to apply these settings (likely due to `storage_serv` being stopped at the time, since that service appears to own the setting's enforcement). Despite the UI failure, no further SATA link timeouts or rebuild interruptions were observed after these settings were attempted. Unclear whether the settings actually took effect or whether the subsequent rebuild success was caused by the full pool recreation, the `libata.force=3.0Gbps` fix, or elimination of the `storage_serv` monitor bug. These settings remain documented as a mitigation worth trying in any future RAID work.
**Why:** RAID rebuild is sensitive to drive timeouts and uninterruptible I/O waits. Hard drive sleep/hibernation and aggressive ATA power management can introduce unexpected latency or link resets during rebuild operations. Disabling them reduces variables during a critical operation, even if the causal connection to the observed failures cannot be definitively proven. The failed UI application was noted but not escalated, since the pool recreation resolved the issue regardless.
**Alternatives considered:** Leave sleep settings enabled and only investigate if failures continue (rejected — proactive elimination of variables seemed prudent given four consecutive failures), assume the settings took effect regardless of the UI error (rejected — worth documenting the discrepancy for future investigation).

### 2026-08-01 - Kinmoon-smb storage credential update on Kuromoon after Kinmoon user password reset
**Decision:** Updated the `Muzakkir` user password in Proxmox's `kinmoon-smb` CIFS storage configuration via `pvesm set kinmoon-smb --username Muzakkir --password` after discovering that the Kinmoon UGOS user account password had been reset during this session (original password was stale/incorrect, preventing SSH login). The correct username casing is `Muzakkir` (capital M), not `muzakkir`. Failure to update Proxmox's credential caused `NT_STATUS_LOGON_FAILURE` when attempting to connect to the restored `proxmox-backups` share; correcting the password resolved the auth failure.
**Why:** Proxmox stores CIFS credentials in plaintext in its storage configuration and uses them for all subsequent mounts of the remote share. When the underlying UGOS user password changes, the stored credential becomes stale and authentication fails until updated. This is not a backup or sync issue, but a required credential refresh to maintain access to a networked storage target.
**Alternatives considered:** Reset the Kinmoon user account back to the old password (rejected — new password was already set; reverting would undo the security action), recreate the CIFS storage config from scratch (rejected — `pvesm set` is simpler and preserves all other settings), bypass CIFS authentication via guest access (rejected — reduces security and is not applicable here).
