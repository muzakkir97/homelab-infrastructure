# Decisions Log

Architectural decisions, strategy calls, and naming choices made during homelab development.

---

### 2026-09-22 - SSH key-based authentication + config aliases instead of self-hosted SSH manager
**Decision:** Implemented SSH key-based authentication across all four core hosts (Kuromoon, Kinmoon, VM 400, Pi-hole) with a single ed25519 keypair (`~/.ssh/id_ed25519_homelab`) and login aliases in `~/.ssh/config` on Minimoon (`kuromoon`, `kinmoon`, `vm400`, `pihole`). This eliminates the need to memorize IPs or passwords and provides password-free access from Minimoon to all four hosts.
**Why:** Solves the stated problem (IP/password fatigue) with zero new attack surface and no dependency on Kuromoon being up. A self-hosted SSH manager (e.g., Guacamole) would require additional infrastructure, a listening port, and would itself be unavailable if Kuromoon fails. SSH config aliases are a standard, minimalist solution.
**Alternatives considered:** Deploy a self-hosted SSH bastion/jump box (Guacamole, Teleport, etc.) — rejected due to infrastructure overhead and single point of failure, Use a password manager to reduce memorization burden — rejected as incomplete; doesn't solve the IP address problem, Keep current manual IP/password approach — rejected as unsustainable for ongoing daily use.

### 2026-09-22 - Tailscale over persistent pfSense firewall rules for Minimoon's cross-VLAN access
**Decision:** After confirming that a Tailscale subnet router already existed on pfSense (advertising VLAN10_MGMT and VLAN30_SERVICES, but with a silently expired auth key), decided to use Tailscale for Minimoon's cross-VLAN access instead of opening persistent firewall rules. Also installed Tailscale directly on Kuromoon (Tailscale IP 100.89.254.28) and VM 400 (100.94.179.99) for redundancy. The three temporary VLAN20_MAIN firewall rules added during the Sept 21 incident (Minimoon → Kuromoon GUI/SSH, Minimoon → Kinmoon web/SSH) were deleted once Tailscale confirmed working.
**Why:** Tailscale trusts revocable device identity (tailnet membership) rather than a spoofable source IP. Given that Minimoon is a daily gaming PC with higher attack surface (mods, cracked game launchers, overlays, etc.), identity-based access control is more defensible than IP-based rules. The existing pfSense subnet route can be instantly revoked or toggled at the device level if Minimoon is ever compromised; a permanent firewall rule cannot. Tailscale also provides encryption in transit and a built-in audit log.
**Alternatives considered:** Keep the temporary pfSense firewall rules as permanent (rejected — IP spoofing risk on a gaming PC is unacceptable; identity-based access is more resilient), Use a VPN client (WireGuard/OpenVPN) on Minimoon (rejected — Tailscale already exists and provides both subnet routing and device-level MFA), Assume Minimoon will never be compromised (rejected — gaming PCs are explicitly higher-risk targets; controls must account for this reality).

### 2026-09-22 - Direct Tailscale install on Kuromoon and VM 400 for access redundancy
**Decision:** Installed Tailscale client directly on both Kuromoon and VM 400, in addition to relying on pfSense's advertised subnet route. This provides two independent network paths to these hosts: the pfSense-advertised route (which assumes pfSense is up and reachable) and direct Tailscale device-to-device connections.
**Why:** Avoids pfSense being a single point of failure for Tailscale-based access. If pfSense suffers a routing/network issue, direct Tailscale connections to Kuromoon and VM 400 remain available. Kinmoon (UGOS appliance) was excluded because direct Tailscale installation is not an UGOS-supported feature; it relies on the pfSense route, which is acceptable since Kinmoon's network card(s) are controlled by UGOS anyway.
**Alternatives considered:** Only use pfSense's subnet route, relying on pfSense's own redundancy/stability (rejected — adds unnecessary risk if pfSense has a problem; direct install is low-cost), Install Tailscale on all four hosts including Kinmoon (rejected — UGOS does not support custom daemon installations), Use only direct Tailscale without the subnet router (rejected — subnet routing is still valuable for network-wide access patterns).

### 2026-09-22 - HTTPS response check + dual LAN/Tailscale paths for Kuromoon watchdog
**Decision:** Implemented the Kuromoon host-freeze watchdog (deployed on Pi-hole, `/usr/local/bin/kuromoon-watchdog.sh`, cron every 2 minutes) to check HTTPS responses (not ICMP ping) from Kuromoon's Proxmox GUI on both the LAN IP (192.168.10.5) and Tailscale IP (100.89.254.28). Alerts via Telegram Bot API after 3 consecutive failures (~6 minutes), distinguishing "both down" (genuine host freeze) from "LAN only down" (routing issue). State is tracked in `/var/tmp/kuromoon-watchdog-{state,failcount}`.
**Why:** Tonight's Sept 21 incident showed that ICMP ping stayed alive while the entire Proxmox application layer was unresponsive — a symptom of either an app-level hang (pveproxy crash) or kernel-level I/O stall, not a network connectivity loss. HTTPS response is more representative of actual service health. Checking both LAN and Tailscale paths distinguishes a genuine host problem from a network-path-specific issue, which informs recovery actions (reboot vs. network troubleshooting). Placing the watchdog on Pi-hole (an independent host) avoids monitoring a host via its own monitoring service, which would fail during the very outage being reported.
**Why not ICMP:** Ping can succeed even when the host is unresponsive at the application layer; Sept 21's incident confirmed this.
**Why not self-hosted ntfy:** ntfy (CT 222) runs on Kuromoon itself; it would be unavailable during exactly the failure it needs to report. Direct Telegram Bot API calls bypass Kuromoon entirely.
**Alternatives considered:** Use ICMP ping — rejected as proven insufficient by tonight's real incident, Check only the LAN path (rejected — can't distinguish routing issues from host freezes), Check only Tailscale path (rejected — provides false confidence if pfSense/VLAN10 has a problem), Use ntfy running on Kuromoon (rejected — single point of failure), Increase check frequency to catch freezes faster (rejected — every 2 minutes is reasonable; faster checks risk false positives and notification spam).

### 2026-09-22 - Telegram Bot API over self-hosted ntfy for Kuromoon watchdog alerts
**Decision:** Used direct Telegram Bot API calls in the Kuromoon watchdog script for failure/recovery notifications, rather than deploying a self-hosted ntfy instance or using another Kuromoon-resident service.
**Why:** ntfy (currently running as CT 222 on Kuromoon) would be unavailable during exactly the failure conditions being reported (host freeze affecting all services). Moving the alert delivery to an independent channel (Telegram Bot) ensures the watchdog can always notify, even when Kuromoon is fully down. Direct API calls also eliminate an additional dependency and single point of failure.
**Alternatives considered:** Use ntfy running on Kuromoon (rejected — unavailable during host freeze), Use email alerts (rejected — slower and less visible than Telegram), Use a webhook to another external service (rejected — Telegram Bot API is already available and sufficient), Log only to a local file (rejected — log wouldn't be useful if no one checks it during the incident).

### 2026-09-22 - Defer EMIYA execution engine and Jeanne "hands" MCP until after Phase 24.11/24.12
**Decision:** Decided not to start building EMIYA's execution engine or Jeanne's MCP "hands" capability before Phase 24.11 (Credential Store Migration) and Phase 24.12 (Jeanne Architecture Refactor) are complete. These phases will formalize a shared MCP tool layer and credential management; building either agent engine before that formalization risks duplicating or rebuilding work once 24.12 finalizes the shared infrastructure.
**Why:** The roadmap already sequences a shared MCP tool layer as a dependency behind 24.12. Building ad-hoc tool-calling for EMIYA now would create technical debt if the later architectural refactor changes that pattern. Waiting ensures EMIYA and Jeanne both use the same standardized approach, reducing maintenance burden and enabling future capability reuse.
**Alternatives considered:** Build a minimal EMIYA engine immediately using n8n-claw patterns (rejected — conflicts with the planned 24.12 architecture; duplication likely), Defer both until 24.13 or later (rejected — waiting longer than necessary; 24.11/24.12 are coming soon and will unblock this), Build Jeanne's hands now and EMIYA later (rejected — same duplication risk; both need the shared layer first).

### 2026-09-22 - Adopt n8n-claw's MCP Bridge, soul personality table, and Heartbeat notify patterns
**Decision:** When designing EMIYA's execution engine and Jeanne's MCP architecture, decided to adopt three patterns from the open-source n8n-claw project: (1) MCP "Bridge" for skill-registration and tool discovery, (2) `soul` personality/behavior table for agent identity configuration, (3) Heartbeat with `always` and `on_change` notification modes for status updates. Explicitly rejected n8n-claw's parallel Project Memory doc store (conflicts with Da Vinci's sole-writer principle) and plaintext credential storage (worse than the planned n8n credential store).
**Why:** These patterns from n8n-claw are well-proven in a similar MCP orchestration context and require no new conceptual work. Adopting them accelerates the design phase and ensures compatibility with existing open-source tool ecosystems. The rejected patterns were problematic for this specific homelab: Project Memory would duplicate Da Vinci's documentation role, and plaintext credentials are a regression from the security model being built.
**Alternatives considered:** Design the entire MCP layer from first principles (rejected — n8n-claw's patterns are already validated; no need to reinvent), Adopt all of n8n-claw's patterns including the rejected ones (rejected — Project Memory and plaintext creds conflict with existing architecture), Use a different reference implementation (rejected — n8n-claw's MCP focus is the best fit among available projects).

### 2026-09-22 - Shortlist local coding models: Qwen2.5-Coder-14B-Instruct and DeepSeek-Coder-V2-Lite-16B
**Decision:** For powering EMIYA's eventual "hands" capability on the RX 6700 XT (12GB VRAM), shortlisted two local coding models for A/B testing: Qwen2.5-Coder-14B-Instruct and DeepSeek-Coder-V2-Lite-16B. Explicitly ruled out Qwen3-Coder-30B-A3B as too large for the VRAM budget, even when quantized, because MoE (mixture-of-experts) models require all experts resident in VRAM regardless of active-parameter count.
**Why:** Both shortlisted models fit comfortably in 12GB VRAM at reasonable quantization levels, have strong tool-calling / function-calling support, and are actively maintained. Ruling out Qwen3's MoE architecture prevents a common gotcha where the reported parameter count is misleading; the full expert set would exhaust VRAM and cause OOM/swapping. The 14B–16B dense-model range is the sweet spot for this hardware.
**Alternatives considered:** Use a larger model (20B+) with aggressive quantization (rejected — quantization loss + MoE overhead make this impractical), Use only proprietary APIs (Claude, OpenAI) (rejected — goal is to have local capability for offline use and cost control), Defer model selection until later (rejected — hardware constraint is known now; narrowing choices now informs the architecture).
